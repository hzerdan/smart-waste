¿Cómo funciona realmente una Invitación de Usuario?

Tu intuición sobre el "pasaporte" es muy acertada, pero la mecánica web tiene una escala intermedia clave: el canje en el servidor de autenticación.

Tu Intuición (Lo que se percibe)

1. Se "prepara una página HTML" especial para cada invitación.
2. El usuario viaja con su token directo a esa página.
3. La página atiende el token y no está logueado, solo presenta el "pasaporte".

La Realidad (Bajo el capó)

1. La página HTML es genérica y única (no se crea una por persona).
2. El clic del email va primero a Supabase (el servidor), no a tu web.
3. Supabase verifica el token, y lo loguea temporalmente antes de redirigirlo a tu pantalla para que cree su contraseña.

El Ciclo de Vida Explicado en 5 Actos

1

Acto 1: El Admin envía la invitación

El Administrador completa el formulario en la app. La Edge Function invite-user llama a Supabase Auth en el servidor con permisos seguros. En ese instante exacto, Supabase realiza dos acciones automáticas:

  • Crea un registro de usuario provisional en la base de datos interna (auth.users), guardando su email, fecha de invitación pero dejando la contraseña vacía y confirmed_at = null.
  • Genera un token criptográfico único y firmado (un hash de un solo uso que expira automáticamente en 24 horas).
auth.users → { email: "usuario@empresa.com", invited_at: "2026-10-14...", confirmed_at: null }
2

Acto 2: El Correo: El Pasaporte y la Parada Oculta

El usuario recibe el correo con el botón "Aceptar Invitación". El enlace que contiene ese botón NO va directo a tu sitio web, sino al servidor de Supabase Auth:

https://scnkevcuphhyetedpuhe.supabase.co/auth/v1/verify?token=XYZ&type=invite&redirect_to=http://localhost:5173/establecer-password

¿Por qué ocurrió el error 404 antes?

Porque cuando no le pasábamos redirect_to explícito, Supabase usaba su valor de fábrica (http://localhost:3000). Como en el puerto 3000 había otro servidor backend corriendo, ese servidor rechazó la petición con Cannot GET /. Al especificar http://localhost:5173/establecer-password, el navegador es dirigido a nuestro frontend de Vite.

3

Acto 3: El Canje en Supabase: Se emite la Sesión

Cuando el navegador del usuario golpea la puerta de Supabase (/auth/v1/verify):

  • Supabase comprueba que el token coincida con el usuario.
  • Quema el token de un solo uso: si alguien vuelve a hacer clic en el mismo email más tarde, ya no servirá.
  • Emite inmediatamente una orden de redirección HTTP 302 hacia el navegador.
"¡Token válido! Navegador, te entrego este access_token de sesión temporal y te redirijo inmediatamente a http://localhost:5173/establecer-password#access_token=...".
4

Acto 4: Aterrizaje en tu Frontend: Establecer Contraseña

El navegador del usuario llega a la pantalla EstablecerPassword.tsx en nuestra aplicación.

  • La librería de Supabase en el frontend detecta el access_token en la URL y reconoce al usuario en memoria: "Bienvenido, sabemos que sos usuario@empresa.com, pero tu cuenta requiere una contraseña para activarse".
  • El usuario no necesita ingresar ninguna contraseña anterior (porque nunca tuvo una). Solo ingresa su nueva clave y la confirmación.
✓

Acto 5: El Registro queda Completo y Activo

Al pulsar "Guardar Contraseña", el frontend ejecuta la llamada a Supabase:

supabase.auth.updateUser({ password: "mi_password_secreta" })

En ese instante ocurren tres transformaciones fundamentales:

  • Se guarda el hash criptográfico seguro de la contraseña definitiva.
  • El campo confirmed_at en la base de datos deja de ser NULL y se sella con la fecha/hora actual.
  • El badge "Invitación pendiente" desaparece de la vista del Administrador porque la cuenta ya está formalmente activa.
  • El usuario es redirigido automáticamente a su Dashboard respectivo según su rol, y en sus próximos ingresos iniciará sesión normalmente con su email y contraseña.
En resumen: No se generan páginas individuales; el token es una llave de un solo uso que viaja al servidor de Supabase para canjearse por una sesión temporal, permitiendo al usuario fijar su contraseña en una pantalla común de tu frontend.
